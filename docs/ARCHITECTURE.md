# Архитектура WebsiteMonitor

## Общая схема

```
                    ┌──────────────────────────────────────────┐
                    │            app/core  (бизнес-логика)     │
                    │  database · models · monitor · scheduler  │
                    │  statistics                               │
                    └───────────────▲───────────────▲──────────┘
                                    │               │
                    ┌───────────────┴────┐   ┌──────┴───────────────┐
                    │   app/services     │   │                     │
                    │ site_service      │   │                     │
                    │ check_service     │   │                     │
                    └────────▲──────────┘   │                     │
                             │              │                     │
              ┌──────────────┴───────────────────────────────┐
              │                SQLite (monitor.db)            │
              └──────▲──────────────────────▲─────────────────┘
                     │                      │
        ┌────────────┴──────┐   ┌───────────┴────────────────┐
        │ APP_WEB (Flask)   │   │ APP_DESKTOP (PySide6)      │
        │ routes,templates, │   │ main_window, dialogs       │
        │ static, Chart.js  │   │ (QPainter-графики)         │
        └───────────────────┘   └────────────────────────────┘
```

Ключевой принцип — **бизнес-логика не дублируется**: обе версии работают только
с модулями `app/core` и `app/services` и используют одну базу данных.

## Описание модулей

| Модуль | Назначение |
|--------|------------|
| `app/core/database.py` | Путь к БД в пользовательской директории (Windows: `%LOCALAPPDATA%\WebsiteMonitor`, Linux: `~/.local/share/WebsiteMonitor`); движок SQLAlchemy, WAL, busy_timeout, общий lock на запись, контекстный менеджер сессии. |
| `app/core/models.py` | Таблицы `monitored_site`, `check_history`, `incident` (SQLAlchemy 2.x `DeclarativeBase`), внешние ключи и индексы. |
| `app/core/monitor.py` | HTTP-проверка (`perform_check`): замер времени, классификация ошибок, ручной обход редиректов с ревалидацией каждого перехода; SSRF-защита (`check_url_allowed`); сохранение результата и управление инцидентами (`apply_check_result`); атомарный захват сайта на проверку (`_acquire_site_check`) для исключения двойных проверок даже между двумя процессами. |
| `app/core/scheduler.py` | Фоновый поток-планировщик: раз в секунду выбирает активные сайты, чей интервал истёк, и отправляет проверки в пул потоков; периодическая очистка «зависших» флагов. |
| `app/core/statistics.py` | Сводка для главной панели, истории, инциденты, метрики (avg/min/max времени, доступность в %) и серии для графиков по периодам 24h/7d/30d — считаются по реальным записям SQLite. |
| `app/services/site_service.py` | CRUD сайтов, валидация полей (URL, интервал), очистка и ограничение истории (5000 записей на сайт). |
| `app/services/check_service.py` | Ручная проверка (`run_check_async`/`run_check_sync`) и периодическое обслуживание истории. |
| `app/web/*` | Flask-фабрика, маршруты (HTML-страницы, POST-действия, JSON API `/api/overview`, `/api/sites`, `/api/statistics`), шаблоны Jinja2, стили и Chart.js (локально в `static`). |
| `app/desktop/*` | PySide6: `MainWindow` (QStackedWidget + боковое меню), страницы (главная, сайты, история, сбои, статистика), диалог добавления/редактирования сайта, простой график на QPainter. |
| `web_main.py` / `desktop_main.py` | Точки входа: инициализация БД, старт планировщика, запуск интерфейса; веб-версия открывает браузер на `127.0.0.1` и завершается по Ctrl+C. |

## Взаимодействие компонентов

1. При запуске обеих версий `init_db()` создаёт таблицы, затем стартует
   `MonitorScheduler` (отдельный поток + пул worker-потоков).
2. Планировщик (или кнопка «Проверить вручную») вызывает `check_site_now(site_id)`:
   - атомарно помечает сайт флагом `is_checking` (условный `UPDATE` — благодаря
     сериализации записей SQLite два процесса не проверят сайт одновременно);
   - выполняет HTTP GET (таймаут 5 с, редиректы обходятся вручную и
     проверяются SSRF-политикой);
   - сохраняет результат в `check_history`, обновляет статус сайта и
     открывает/закрывает инцидент.
3. Интерфейсы только читают агрегаты через `app/core/statistics` — тяжёлая
   работа (сеть) никогда не выполняется в потоке интерфейса.
4. Веб-версия слушает только `127.0.0.1`; браузер открывается автоматически.
5. Обе версии используют один файл `monitor.db`, поэтому могут работать
   одновременно (WAL + busy_timeout + условные обновления).

## Потокобезопасность SQLite

- Режим WAL: чтение и запись можно вести параллельно.
- `busy_timeout = 30 c`: конфликтующие писатели ждут, а не падают.
- Общий `threading.RLock` в `DatabaseSession` упорядочивает записи внутри
  процесса; межпроцессную согласованность обеспечивает сам SQLite.
- Флаг `is_checking` сбрасывается в конце проверки; планировщик периодически
  чистит «зависшие» флаги после аварийного завершения.

## Безопасность

- SSRF-политика: схема только http/https; hostname разрешается через DNS и
  каждый IP проверяется (`is_loopback/is_private/is_link_local/multicast/
  reserved/unspecified`, включая 127.0.0.0/8, 169.254.0.0/16, 192.168/16, 10/8,
  ::1, fd00::/8 и т.д.); редиректы проходят ту же проверку. Обход для локальных
  демонстраций: `WEBSITE_MONITOR_ALLOW_PRIVATE=1`.
- Ввод валидируется (название 1–200 символов, URL ≤ 2048, интервал 5…
  604800 с); запросы к БД выполняются через SQLAlchemy (без конкатенации SQL).
- Таймаут проверки фиксирован (5 с), размер истории ограничен (5000 записей на
  сайт), старые записи удаляются автоматически.
- Ошибки логируются через `logging`; некритичные сбои не роняют планировщик.
